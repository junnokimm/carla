## 2. 경로 선정 변경

### 연결된 곡선을 지역적인 방향 변화로 검사

기존 코드는 수백 미터 경로의 모든 waypoint를 최초 방향과 비교했다. 완만하게 휘어도 누적 8°를 넘으면 전체 후보가 탈락했다.

수정본은 연속한 waypoint의 전방 방향, 실제 두 점 사이 진행 방향, 직전 segment 방향을 비교한다. 각 지역 변화에 8° 제한을 적용하므로 완만한 누적 곡선을 허용한다. 실제 역진행·비진행·급격한 꺾임은 거절하며, 현재 ego와 시작 waypoint 사이 15° 방향 검사는 유지한다.

### junction 표식과 실제 분기를 구별

`is_junction`만으로 시작·진행·인접 차로를 거절하지 않는다. 실제 Driving 연결과 방향, 인접 차로변경 허용 여부를 검사한다.

후보 중 road/section/lane/pose가 모두 같은 항목만 중복으로 제거한다. 서로 다른 Driving 후보가 둘 이상이면 `AMBIGUOUS_FORK`, 하나도 없으면 `DISCONNECTED`로 거절한다. 임의로 첫 분기나 직진처럼 보이는 분기를 선택하지 않는다.

source와 target 양쪽에서 중심선 segment의 실제 3차원 자기교차도 검사한다. 고도가 다른 교차는 구별한다. 이 검사가 서로 가까이 접근하지만 교차하지 않는 모든 임의 경로의 투영 유일성을 증명하는 것은 아니다.

### 곡선·경사에 맞춘 위치 계산

경로 station, 가장 가까운 점 투영, 진행 접선을 3차원 segment와 일치시켰다. 차로변경 중에는 source/target segment를 이용하고, pitch와 waypoint roll을 보존한다. 예상 노출 위치의 높이도 미래 도로면과 현재 차량의 도로면 오프셋을 사용한다.

TTC의 접근 속도는 3차원 도로 진행 접선과 실제 속도 벡터의 내적으로 계산한다. 계산값을 목표 TTC에 맞춰 덮어쓰지 않는다.

## 3. 준비 로직 변경

### 같은 예정 시각에 남은 준비 시간을 사용

노출 예정 시각은 기존 seed로 400–600초 범위에서 한 번 정한다. 준비 시도마다 새 시각을 추첨하지 않는다.

기본 설정에서 준비 시간은 6초로 시작한다. 첫 후보가 거절되어 예정 시각이 가까워지면 5초, 4초, 최소 3초 범위에서 남은 시간을 사용한다. 최소값은 현재 설정의 차로변경 시간 3초를 사용한 구현상 하한이다. 실장비에서 검증한 연구 기준을 새로 정의한 것은 아니다.

`preparation_s = min(config.preparation_s, max(config.lane_change_s, planned - elapsed))`

이미 예정 시각을 지났으면 최소 준비 시간을 확보하고, 실제 조정 목표 시각은 `max(planned, elapsed + preparation_s)`로 기록한다. **실제 노출 시각의 분포가 균등하다고 해석해서는 안 된다.** 예정 시각과 조건부 지연이 구분되어 기록된다.

기본 설정에서는 600초 마감에 맞추기 위한 마지막 준비 가능 시점이 계산상 약 597초다. 프레임 지연과 실제 최초 노출 판정 때문에 그 시점에 실제 노출 성공이 보장되는 것은 아니다. 600초를 넘는 준비 후보는 예약·생성 전에 거절하고, 실제 첫 노출도 기존의 400–600초 검사로 판정한다.

### 장면에 필요한 경로를 계산

이전의 고정 6초 준비와 넓은 거리 합산 대신 선택한 준비 시간으로 cargo 위치를 계산한다. 필요한 경로 길이는 cargo 위치뿐 아니라 lead의 준비 및 차로변경 이동량, 기존 Traffic Manager handoff 여유, 조향 lookahead까지 포함한다. 짧은 준비 후보를 선택했다고 lead가 이동을 마치기 전에 경로 끝에서 제어를 넘기지 않도록 검증했다.

### 생성 전에 가림 가능성을 검사

경로 조건만 완화하면 곡선에서 cargo가 lead 옆으로 먼저 보일 수 있다. 이 문제를 줄이기 위해 경로 선정 후, 사건 예약과 actor 생성 전에 초기 가림과 준비 중 좌우 가림 범위를 예측한다.

기본 lead는 현재 ego와 같은 `vehicle.mercedes.coupe_2020` 자산이다. 이 경우 실제 ego의 측정된 bounding box를 lead 사전 검사의 근거로 사용한다. 다른 자산의 크기를 임의 추정하지 않으며, 서로 다르면 `LEAD_PREVIEW_BOUNDS_UNAVAILABLE`로 보류한다.

생성 전에는 기존 보수적 cargo envelope를 사용한다. 이것은 cargo 자산의 실제 크기를 변경하는 동작이 아니다. 시작 순간에는 전체 가림, 준비 기간에는 좌우 envelope를 검사한다. 생성 후 숨겨진 실제 배치가 끝나면 lead와 cargo의 실제 bounding box로 전체 준비 접근을 다시 검사한다. 실제 자산 가림 검사 실패는 기존 오류 종료·정리 경로로 처리하며 다른 사건을 반복 생성하지 않는다.

## 6. 남은 파일럿 검증

이 수정본은 기존 실패 원인에 대응하는 구현과 자동 회귀 검증을 마친 파일럿용 후보이다. 실제 Town04 주행과 Windows/TS-XW 장비에서의 위험사건 노출은 다음 파일럿 결과로 확인해야 한다.

모든 자유 주행 경로와 정차 상태에서 사건을 보장하는 구현은 아니다. 실제 다중 분기, 정차, 다른 차량의 점유, 가림 불충족 등이 시간창 내내 이어지면 `NOT_OCCURRED`가 남을 수 있다. 예를 들어 합성 R1000 m 곡선에서는 짧은 준비 후보가 성공했지만, 같은 기본 headway의 R500 m 곡선 사례는 끝까지 거절되었다. 이 결과를 실제 Town04 성공률로 바꿔 해석해서는 안 된다.

TTC 목표 설정값 4초는 유지했으나 실제 최초 노출 TTC가 정확히 4초라고 보장하지 않는다. 관측값은 실제 clearance와 closing speed에서 계산하며, 실장비 최초 노출과 운전자 반응 기록으로 다시 확인한다.

파일럿에서 확인할 핵심은 다음 세 가지다.

1. 같은 `run_pilot.cmd`로 훈련 → 모듈 1 → 모듈 2 → 결과 ZIP 저장을 완료한다.
2. 모듈 2에서 lead가 옆 차로로 이동하며 앞의 cargo가 노출되는지 확인한다.
3. 결과 ZIP의 예정 시각·준비 시작·첫 geometry·display 노출·실제 TTC를 함께 비교한다. 눈으로 사건을 봤다는 사실만으로 실험 기록의 유효성을 판정하지 않는다.

현재 사용자 설정의 P5 시간창, 모듈 시간, 키보드/TS-XW 입력과 실행기 경로는 이번 덮어쓰기 대상에 포함하지 않는다. 늦은 출구 안내, M2 배정 조건과 실제 NoA 사용의 일치 여부, 동적 엔진 오디오는 이번 수정으로 해결했다고 표시하지 않는다. 오디오는 사용자가 정한 파일럿 이후 작업으로 남긴다.
