# 2026-10-17 P8 파일럿 수정본: 입력 복구와 단일 실행 경로

## 이번 배포의 결론

최신 첨부본 `carla(20261017-072209).zip`에서 W/페달 입력이 차량 가속으로 이어지지 않은 직접 원인을 확인했다. TS-XW 브레이크 채널의 초기 값 `0.0`이 계속 들어왔고, 기존 정규화가 이를 `brake=0.5`로 변환했다. 브레이크 우선 정책 때문에 W가 입력되어도 최종 차량 명령의 throttle은 0이었다.

## 1. 적용 및 고정 명령

### 처음 한 번 적용

배포 ZIP은 기존 프로젝트 루트에 덮어쓰는 수정본이다. 원본 폴더 전체나 Python 가상환경을 새로 만드는 파일이 아니다. 기준 프로젝트는 최신 실행 기록의 `C:\dev\carla`이며, ZIP 안의 `src`, `tests`, `tools`, `config`, `docs`, `run_pilot.cmd`가 그 폴더 바로 아래에 놓여야 한다.

PowerShell에서, ZIP을 기본 다운로드 폴더에 저장했다면 다음을 한 번 실행한다.

```powershell
Expand-Archive -LiteralPath "$env:USERPROFILE\Downloads\carla_pilot_fix_20261017.zip" -DestinationPath "C:\dev\carla" -Force
```

다른 위치에 내려받았다면 `-LiteralPath`에 실제 ZIP 경로를 넣는다. 파일 탐색기에서 ZIP의 내용을 `C:\dev\carla`에 복사하고 같은 이름의 파일을 교체해도 된다. 기존 데이터, 가상환경, native 바이너리는 배포 ZIP에 포함되지 않는다.

### 매번 실행하는 명령

기존 CARLA 서버가 **Town04**로 실행 중인 환경에서:

```powershell
C:\dev\carla\run_pilot.cmd
```

이미 프로젝트 폴더에 있다면 다음도 동일하다.

```powershell
.\run_pilot.cmd
```

실행기는 자기 파일이 있는 프로젝트 폴더로 이동하고, 최신 기록에서 확인한 아래 interpreter로 기존 `src.p8.operator_cli`를 실행한다.

```text
C:\dev\carla-native-tm-cancel-20261012\.venv-p8\Scripts\python.exe
```

이 경로의 검증된 native P8 환경이 없으면 이유를 출력하고 종료한다. CARLA 서버 또는 Unreal Editor의 설치·시작은 이 실행기의 범위에 포함되지 않는다. 첨부 소스에는 해당 서버를 자동 시작할 검증된 설치 경로가 없다.

### 최초 실행 시 M2 설정 두 개

최신 실행 로그에는 M1 P5 시간창 `0..600초`가 있지만 실제 M2 P5 시간창 값은 남아 있지 않다. 따라서 `config/p8_pilot.json`에서 M2 두 값을 `null`로 두었다. 최초 실행 시 기존 실험 설정의 다음 두 값을 입력하면 같은 JSON 파일에 저장한다.

- `M2 P5 open 초`: M2 시작 후 진출 안내가 가능해지는 시각.
- `M2 P5 close 초`: M2 시작 후 진출 안내를 허용하는 마지막 시각.

`0 <= open < close <= 780`이어야 한다. 이것은 **P5 진출 안내 시간창**이며, 위험사건의 무작위 400~600초 시간창과 서로 다른 설정이다. 문서에 없는 연구값을 편의상 확정하지 않았다. 부적합한 입력이나 저장 실패가 있으면 주행을 시작하지 않고 기존 설정 파일을 보존한다. 정상 저장 후에는 다시 묻지 않는다.

## 2. 화면에서 진행하는 순서

1. 명령 실행 후 운전 장치 준비 화면이 나오면 그 창을 클릭한다. 가속 페달과 브레이크 페달을 각각 한 번 밟았다 완전히 떼고, W/다른 키와 핸들 버튼을 놓는다. 정상 해제 상태가 확인되면 자동으로 주행으로 넘어간다.
2. 훈련은 600초다. 먼저 W로 가속, 페달로 가속, 실제 브레이크 제동을 확인한다. 훈련을 일찍 마치려면 기존 F8을 사용한다.
3. `Tobii 외부 보정` 화면은 외부 절차의 경계를 기록한다. SPACE로 다음 안내에 간다. 이 화면 자체가 실제 보정·시선 수집 성공을 확인하지 않는다.
4. M1 안내에서 SPACE를 누른다. 장치를 새로 열므로 입력 준비를 다시 확인하고, 완료 후 M1 600초가 시작된다.
5. 휴식 화면은 약 120초를 권한다. 기존 운영 사양대로 강제 최소 대기 없이 SPACE로 M2 안내에 갈 수 있고 실제 휴식 시간은 기록된다.
6. M2 안내에서 SPACE를 누른다. 입력 준비를 다시 확인한 뒤 M2 780초가 시작된다. `NOA_L2` 조건의 초기 NoA ON도 준비 완료 후 적용된다.
7. M2 안에서 전용 seed/RNG로 400~600초 중 예정 노출 시각 하나를 선택한다. 준비 조건이 맞으면 선행차가 비켜나며 정지 장애물이 드러나는 사건을 실행한다. 반응·정지 이후에도 같은 M2를 780초까지 유지한다.
8. 완료 화면에 원자료 폴더와 ZIP 경로가 나온다. 창을 닫으면 콘솔에도 `RESULTS_EXPORTED`와 실제 경로가 출력된다. ZIP은 종료 화면을 닫기 전에 이미 만들어진다.

준비 중 Esc 또는 창 닫기는 세션 중단으로 기록한다. 페달을 떼어도 계속 `확인 대기`이면 해당 축에서 정상 해제 값이 아직 관측되지 않은 것이다. 그 상태에서 주행 시간을 소모하지 않는다. Esc로 종료한 결과 ZIP의 준비 실패/취소 이벤트에 마지막 raw 값, 포커스, 키 해제 상태와 대기 시간이 남는다. 실제 장치 축이 계속 잘못된 값을 내보내는 경우까지 소프트웨어가 정상으로 간주하지는 않는다.

## 4. 첫 번째 문제의 근거와 수정 이유

근거 실행은 `data/p8_operator/P8-M2-V1-72b04ff08b9d41249485dbb830a441ca`다. 배포본의 `docs/pilot_verification/input_evidence.json`에 원자료 해시, 실제 파일명, CSV 행번호와 집계가 들어 있다.

| 관측 항목 | 최신 실행 집계 |
|---|---:|
| `tsxw_input_sample` | 8,677개 |
| 그중 `raw.brake == 0.0` | 8,677개 전부 |
| 정규화된 페달 brake | 8,677개 전부 0.5 |
| 키보드와 병합한 effective brake | 0.5가 8,669개, S 입력으로 1.0이 된 8개 |
| W override를 관측한 샘플 | 158개 |
| W를 누른 때 병합 throttle | 최대 1.0 |
| `tsxw_manual_control`의 전송 throttle / brake | 전부 0.0 / 0.5 |
| 차량 telemetry 행 | 8,679개, throttle 0.0 / brake 0.5 |

기존 페달 매핑에서 해제 방향은 +1이고 완전히 밟은 방향은 -1이다. `raw=0`을 정규화하면 `(1 - 0) / (1 - (-1)) = 0.5`다. 키보드 W는 throttle만 override하고 실제 브레이크는 유지하기 때문에, 최종 `POSITIVE_BRAKE` 우선 처리에서 throttle이 0으로 억제된다. 이 경로를 원본 로그 샘플로 재현했다.

가속 페달 채널은 0.0에서 0.966644287109375로 바뀐 기록이 있다. 그러나 이것만으로 물리 페달의 전 구간 동작이나 보정이 정상이라고 결론내릴 수는 없다. 최신 실행에는 실제 M2 주행 입력·telemetry가 없다.

`32767/32768`이 +1보다 약간 작은 SDL 끝점인 경우를 brake=0으로 처리하는 보정은 원본에 이미 있었다. 이번 최신 로그 문제는 그 값이 아니라 `0.0`이 지속된 경우다. 따라서 끝점 보정을 반복하거나 raw=0을 무조건 ‘브레이크 해제’로 바꾸면 실제 절반 제동까지 무시하게 된다.

이번에는 다음 순서로 수정했다.

1. SDL 창을 먼저 준비하고 장치 이벤트를 지속적으로 처리한다.
2. 포커스, 명령 키/버튼 해제, 양 페달의 기존 해제 끝점이 연속 두 번 확인될 때까지 차량을 제동 상태로 유지한다.
3. 준비에 사용한 창과 조이스틱 핸들을 해당 주행에서 재사용한다.
4. 훈련뿐 아니라 M1/M2의 새 장치 열기에도 같은 준비를 적용한다.
5. 준비 후 주행·P5·M2 hazard의 기준 시각 및 초기 NoA를 시작한다.

연속 두 샘플은 장치 준비 확인 조건이며 연구 반응 임계값이나 페달 deadzone 변경이 아니다. 기존 raw 값, 브레이크 우선 정책, TS-XW/NoA override 의미는 유지한다. Windows/SDL 드라이버 내부에서 초기 값이 지속된 정확한 이유는 실제 장비에서 확인하지 못했다.

공식 pygame 문서도 조이스틱 상태 갱신을 위해 이벤트 큐를 자주 처리하도록 명시한다. 이 문서는 변경의 API 근거이며, 특정 SDL 버전의 결함을 입증하는 자료는 아니다.

- [pygame joystick](https://www.pygame.org/docs/ref/joystick.html)
- [SDL initial axis state](https://wiki.libsdl.org/SDL2/SDL_JoystickGetAxisInitialState)
- [CARLA 0.9.16 API](https://carla.readthedocs.io/en/0.9.16/python_api/)

## 5. 추가 수정 사항

### M2 원시 입력 CSV 크기

60Hz 원시 입력·geometry를 한 이벤트의 JSON 필드에 모으면 약 132,017~141,021자가 되어 기본 CSV 필드 한도 131,072자를 넘었다. 주행 후 모듈 집계나 manifest 검사에서 `_csv.Error`가 발생할 수 있었다.

원시 샘플 배열을 65,536자 예산 이내의 연속 묶음으로 나눈다. 원시 샘플을 버리지 않고, 성공적으로 기록한 앞부분만 버퍼에서 제거한다. 최종 60Hz 통합 재현에서는 원래 452개 샘플이 23개 묶음에 순서·개수 그대로 남았고, raw JSON 최대 65,204자, scene/services 정보를 포함한 실제 CSV 필드 최대 65,617자로 기본 reader에서 읽혔다.

저장 완료 여부가 불확실한 I/O 오류는 정상 원자료로 취급하지 않는다. 마지막 raw 저장의 실패는 hazard 요약의 `execution_status=FAILED`, `partial_data=true`, `error`와 `raw_storage`에 반영한다. 같은 샘플 묶음을 재시도할 때 같은 `batch_id`와 샘플 범위를 유지하고 `write_attempt_id`를 새로 부여한다. 쓰기 자체는 성공하고 flush만 실패한 경우 같은 배치의 중복 행이 있을 수 있으므로, `possible_duplicate_batches`와 `batch_id`를 확인해야 한다. 정상 저장 검증에서는 누락·중복이 없었다.

### 자동 ZIP 및 결과 상태

`SessionServices` 로그 close → 최종 manifest 저장 → 해당 실행 ZIP 생성 순서다. UI와 CLI에 실제 경로 및 내보내기 실패가 전달된다. 실제 실행의 자료 출처가 기본 `DEV_STUB`로 오표기되는 호출부도 현재 `ACTUAL_BOUNDED_OPERATOR` provenance를 전달하도록 수정했다.

### 단일 실행기

기존 `operator_cli.main()`에 검증된 고정값과 설정 파일 값을 전달한다. native 바이너리 해시, TM owner, route, CLI 검사를 기존대로 거친다. M1/M2의 명목 시간을 줄이는 인자를 넣지 않는다. 첫 설정 저장은 같은 디렉터리의 임시 파일을 완성한 뒤 교체한다.

## 6. 개발 단계 평가

백분율은 기능 수와 검증 완료를 혼동시키므로 부여하지 않았다. 현재 구현과 실제 실험 가능 여부를 나누면 다음과 같다.

| 단계 | 구현되어 있는 부분 | 남은 확인/구현 |
|---|---|---|
| P1 주행 기반 | 차량 생성, 입력, 제어권, 수동/NoA 제어 경로. 이번에 장치 준비 경계 보완 | 실제 Windows에서 W/가속/제동과 단계 전환 후 재입력 확인 |
| P2 운전자 화면 | cockpit, HUD, mirrors, 렌더링 경로 | 기존 camera/mirror 기대값과 테스트 불일치; P6 AOI와 실제 미러 위치 불일치 |
| P3 NoA 상호작용 | native TM 연결, ON/OFF, override, lane-change 제어와 검사 | 위험사건 actor가 존재할 때 일반 Z/X 자동 차선변경 차단과 현장 동작 확인 |
| P4 세션/시간/로그 | 등록·조건·run ID·단계 기록·CSV·구간 집계 | 분석 가능 상태와 단순 프로그램 종료는 분리해야 함 |
| P5 진출/차선변경 | route manifest, 시간창, 안내/응답/진출 기회 기록, M1/M2 연결 | M2 운영 시간창 값 확정 및 실제 경로에서 위험사건과 함께 실행 검증 |
| P6 Tablet/시선 | 별도 tablet·Tobii·AOI·보정 관련 모듈과 외부 절차 경계 | 실제 수집이 현재 P8 operator에 연결되어 있지 않음. AOI 불일치도 남음 |
| P7 교통/위험사건 | M2 내부 선행차·정지 장애물 준비/노출, 후보 TTC/가시성, 원시 관측 기록 | 물리 노출, 자동 제동/추종 영향, 최초 실제 화면 노출, 연구 유효 반응/결과 검증 |
| P8 통합 | 연속 Training→M1→REST→M2, 이번 단일 실행기·ZIP 내보내기 | 실제 장비에서 전 구간 완료 확인 및 P6/본실험 통합 |

현재 단계는 **P8 통합 개발본이 존재하고, 주행·자료 저장을 막는 결함을 수정해 기능 파일럿을 확인할 단계**다. 정식 참가자 실험 프로그램을 완성했다고 표시할 단계는 아니다.

## 7. M2 위험사건의 구현과 제한

최신 우선 사양은 `docs/CARLA_Experiment_Design_v5_Source_of_Truth.md`의 **2026-10-17 사용자 지정 개발 v1 덧붙임**이다. 오래된 고정 시점·별도 FINAL_HAZARD 설명보다 이 덧붙임을 우선했다.

실제 연결은 nominal M2의 `operator_execution.py`에서 `OperatorM2Hazard`를 구성하고 `MovingHazardBackend`로 actor를 준비하는 경로다. 훈련·M1에 이 장면을 넣지 않는다. 전용 RNG/seed로 M2 active 400~600초의 예정 노출 하나를 선택하며, 선행차가 비켜난 뒤에도 M2는 780초까지 계속한다. 종료 뒤 legacy hazard를 추가 실행하지 않는다.

다만 다음은 남아 있다.

- 차속, 긴 직선 구간, 같은 방향 인접 차선, 교차로/분기/점유 상태, P5/차선변경 진행 여부 등 준비 조건을 만족해야 한다. 6초 준비를 위한 시간이 부족하면 600초 이내 노출이 불가능하다. 사건을 매번 강제로 발생시키는 구현이 아니며 `NOT_OCCURRED`가 가능하다.
- hazard actor가 존재하면 기존 `EMPTY_REHEARSAL` inventory gate가 일반 Z/X 자동 차선변경을 차단한다. lead actor가 M2 끝까지 남는 조건에서는 이 차단도 유지될 수 있다. 수동 조향·제동/NoA 버튼 처리와는 별도다. native gate를 이번 입력 수정에서 완화하지 않았다.
- ego-cargo TM collision detection을 끄는 코드가 존재하지만, 실제로 장애물 앞에서 자동 제동이나 선행차 추종에 의한 감속이 없어지는지는 실주행 확인이 필요하다.
- geometry 기반 가시성 및 TTC는 후보값이다. 참가자 화면에서 최초로 보인 정확한 시각이나 연구상 유효 반응으로 확정하지 않았다.
- 제공된 실행 manifest에서는 실제 hazard 관측 결과를 확인하지 못했다. 이번 오프라인 통합 검증은 실제 사건 노출의 현장 증거가 아니다.

엔진음은 요청대로 이번 수정 범위에 넣지 않았다. 동적 차량 엔진음은 파일럿 이후 몰입감 개선 과제로 남아 있다.

## 8. 검증 결과와 증거

검증 환경은 Python 3.12.14 / pygame 2.6.1 / CARLA 0.9.16 Python 패키지를 갖춘 Linux이며, 실제 CARLA 서버와 TS-XW 장치는 없다. fake CARLA/SDL 검증은 코드 순서·정책·저장 경계를 검증한다.

배포본의 `docs/pilot_verification`을 참조한다.

- `full_suite.txt`: 수정본 전체 suite의 실제 출력.
- `baseline_confirmed.txt`: 실패한 동일 node ID 10개를 원본에서 실행한 비교 증거.
- `input_evidence.json`: 최신 실제 원자료 집계, 해시, 행번호.
- `checks.json`: 최종 검사 명령, 요약 결과, 배포 파일 목록.

최종 전체 suite는 **2,065 passed / 10 failed / 1 skipped (23.59초)**였고, 변경 Python 파일 23개의 Ruff 검사는 통과했다. 정확한 명령과 결과는 `checks.json`에 기록했다. 실패 10개는 화면/camera 및 P6 AOI 불일치 7개, Linux에서 Windows 경로·WinDLL API를 검사한 3개다. 같은 원인으로 원본에서 10/10 재현했으며 이번 수정으로 새로 만든 실패와 구분했다. 관련 없는 화면/연구 AOI 정책을 테스트를 통과시키기 위해 임의 변경하지 않았다.

중점 회귀 검증은 다음 동작을 포함한다.

- 초기 raw=0 지속 시 준비 대기, 정상 해제 후 시작, 창 포커스·키·버튼 해제.
- W와 가속 페달 각각 throttle 전달, 실제 brake의 우선 처리 보존.
- 훈련/M1/M2에서 새 장치 준비 및 준비 후 같은 핸들·창 재사용.
- 준비 17/25초가 600/780초 명목 주행 시간을 잠식하지 않음.
- M2 초기 NoA가 장치 준비보다 먼저 켜지지 않음.
- 준비 중 취소·분리·후속 초기화 실패 시 자원 정리와 부분 결과 내보내기.
- 60Hz raw CSV를 기본 reader, 구간 집계, 결과 audit로 끝까지 읽음.
- 원시 샘플 순서·개수 보존 및 저장 오류 상태/재시도 식별.
- 종료·중단 ZIP의 최종 manifest와 원자료 바이트 일치, 기존 ZIP 충돌 및 저장 실패.
- 고정 실행기가 실제 parser/runtime을 호출하며 명목 시간/기존 정책을 유지.

실제 장비에서는 훈련 시작 직후 W/페달 이동과 브레이크를 우선 확인한 뒤, 같은 실행으로 M1→M2→ZIP까지 진행하면 된다. 새 결과 ZIP이 이번 수정의 현장 검증 근거가 된다.
